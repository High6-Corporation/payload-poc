## 1.1 Production Login Fix

**Symptom:** Logging in at `https://apir-tayo.vercel.app/portal/login` returned "Cannot connect to the server."

**Root cause:** The login page was a Client Component making a direct browser fetch to payload-poc using `NEXT_PUBLIC_PAYLOAD_API_URL`. This is a cross-origin request. Payload has no CORS headers for the apir-tayo origin, so the browser blocked the preflight.

**Fix:** Added `app/api/portal/login/route.ts` — a server-side proxy:
- Receives `{ email, password }` from the browser (same-origin, no CORS issue)
- Server-side fetches `${PAYLOAD_API_URL}/api/portal-clients/login` (server-only env var)
- Resolves `tenantId` from the response (handles both populated object and bare string `user.tenant`)
- Sets `portal_token` + `portal_tenant_id` httpOnly cookies directly
- Returns a generic error message on failure — does not leak raw errors to the client

**Left as-is:**
- `app/api/portal/session/route.ts`'s `POST` handler is dead code. `DELETE` handler is still live for logout — do not remove the whole file.
- `NEXT_PUBLIC_PAYLOAD_API_URL` is still required — `TestimonialsSection.tsx` and `PortfolioSection.tsx` use it client-side for `resolveImageUrl()`.
- Login error messages are not differentiated (bad credentials, lockout, downtime all look the same). Minor UX gap, not a blocker.

**Unrelated adjacent fix:** payload-poc's `NEXT_PUBLIC_SERVER_URL` was confirmed empty in production. Fixed via `getServerSideURL()` adding `VERCEL_PROJECT_PRODUCTION_URL` as a fallback. Distinct from the login CORS bug — do not conflate.

### Multi-tenant model

```
Tenant ("High6 Corporation")
  └── Site ("apir-tayo")          ← PAYLOAD_SITE_ID = 6a352f382054dfd250819c26
        ├── FAQs
        ├── Testimonials
        ├── Portfolio Items
        ├── Pricing Plans
        └── Site Settings (one record per site)
  └── Site ("future-project-2")
        └── ...

PortalClients (separate auth collection)
  └── email + password (Payload-managed)
  └── tenant (relationship → Tenants)
```

### Key design decisions
| Decision | Rationale |
|---|---|
| REST API (not GraphQL) | Simpler, no client dependency needed |
| Server-side fetch (not client) | SEO, performance, ISR caching |
| `next: { revalidate: 60 }` | 60-second stale-while-revalidate |
| `null` on failure (not throw) | Page must render even when Payload is down |
| Payload in separate repo | Independent deploy cycles, shared across projects |
| PortalClients separate from Users | Clients can never get Payload admin access |
| Confirmation before PATCH/POST | All agent mutations require explicit client confirmation |
| Persistent audit log | AgentAuditLog collection records every confirmed change |
| Sequential field collection | One field per turn for creates — consistent, debuggable, avoids parsing ambiguity |
| SiteSettings as collection (not Global) | Native Payload Globals cannot be scoped per tenant/site — multi-tenant plugin only operates on collections |

### `getServerSideURL()` fallback chain (payload-poc)
```ts
export const getServerSideURL = () => {
  return (
    process.env.NEXT_PUBLIC_SERVER_URL ||
    (process.env.VERCEL_PROJECT_PRODUCTION_URL
      ? `https://${process.env.VERCEL_PROJECT_PRODUCTION_URL}`
      : 'http://localhost:3000')
  );
};
```
Priority: (1) `NEXT_PUBLIC_SERVER_URL` → (2) `https://{VERCEL_PROJECT_PRODUCTION_URL}` → (3) `http://localhost:3000`.

## 5. AI Agent Client Portal

### 5.1 Portal architecture

```
Client browser
  └── /portal/login (apir-tayo)
        ↓ POST /api/portal/login (apir-tayo proxy)
              ↓ POST /api/portal-clients/login (payload-poc)
              ↓ JWT + tenantId stored as httpOnly cookies
  └── /portal/chat (apir-tayo, protected by middleware)
        ↓ POST /api/portal/agent (apir-tayo proxy)
              ↓ reads portal_token + portal_tenant_id cookies
              ↓ POST /api/agent (payload-poc)
                    ↓ DeepSeek parses intent
                    ↓ dry-run: returns proposal
                    ↓ confirmed: PATCH/POST + audit log
```

### 5.2 Session cookies
| Cookie | Value | Set by |
|---|---|---|
| `portal_token` | Payload JWT | `POST /api/portal/login` in apir-tayo |
| `portal_tenant_id` | Tenant ID (resolved from PortalClient.tenant) | same |

Cookie options: `{ httpOnly: true, path: "/", sameSite: "lax", secure: process.env.NODE_ENV === "production" }`.

`user.tenant` can be a populated object `{ id }` or a bare string — both are handled in the login proxy.

### 5.3 Agent capabilities

The agent supports **16 actions** across 5 collections:

| Collection | Update actions | Create actions |
|---|---|---|
| Posts | `update_post_title` | — |
| Pages | `update_page_title` | — |
| FAQs | `update_faq_question`, `update_faq_answer` | `add_faq` |
| Testimonials | `update_testimonial_quote`, `update_testimonial_name`, `update_testimonial_position` | `add_testimonial` |
| Portfolio Items | `update_portfolio_title`, `update_portfolio_category`, `update_portfolio_url` | `add_portfolio_item` |
| Pricing Plans | — | `add_pricing_plan` |
| Media | `link_image` | — |
| — | `list_faqs`, `list_testimonials`, `list_portfolio_items` | — |

**Create action field definitions:**

| Action | Required fields | Optional fields |
|---|---|---|
| `add_faq` | `question`, `answer` | — |
| `add_testimonial` | `name`, `quote` | `position` |
| `add_portfolio_item` | `title`, `category` | `url` |
| `add_pricing_plan` | `label`, `price` | `description`, `features` (comma-separated → items array) |

**What the agent cannot do (enforced at route level):**
- Delete records
- Create records for Posts or Pages
- Modify collection schemas or frontend code
- Reassign content between tenants
- Access records outside the authenticated tenant

### 5.4 Conversation flows

**Standard update flow:**
```
Client: "Update the FAQ about pricing"
Agent:  → list_faqs → returns numbered list of tenant-scoped FAQs
Client: "2"
Agent:  → resolves to record ID internally → proposes change
Client: "confirm"
Agent:  → executes PATCH → writes AgentAuditLog → returns success
```

**Create flow (full-prompt — Phase 10, confirmed working):**
```
Client: "Add a FAQ, question is 'How do I get started?' and answer is 'Contact us via email.'"
Agent:  → pre-fills both fields from structured `fields` map → goes straight to proposal
Client: "confirm"
Agent:  → executes POST → writes AgentAuditLog → returns success
```

**Create flow (sequential step-by-step — working fallback):**
```
Client: "Add a new FAQ"
Agent:  → "What would you like the question to say?"
Client: "How do I get started?"
Agent:  → "What should the answer be?"
Client: "Contact us via email and we'll reply within 24 hours."
Agent:  → proposal → client confirms → POST + audit log
```

**Cancellation during awaiting_fields:**
```
Client: "Add a new FAQ"
Agent:  → "What would you like the question to say?"
Client: "Update a testimonial"   ← command verb detected
Agent:  → "Got it, I've set that aside. What would you like to do?"
         → processes as fresh command. No partial record created.
```

### 5.5 Record resolution convention

When a client picks a record from a list, ChatWindow resolves the selection to an internal ID and appends it to the next agent call:
```
message: "update the quote [resolved id: 64abc123...]"
```
The SYSTEM_PROMPT instructs DeepSeek to extract `[resolved id: x]` and use it directly as the `id` field — the client never sees the ID.

### 5.6 Guardrails
- All mutations are two-phase: dry-run (proposal) → confirmed (execute)
- Tenant scoping enforced on every action — 403 if record belongs to a different tenant
- Every confirmed change writes an immutable `AgentAuditLog` record
- Image uploads proxied through apir-tayo — browser never calls payload-poc directly

### 5.7 `awaiting_fields` state machine (Phase 9)

**Backend (`src/app/api/agent/shared.ts`):**
- `CREATE_FIELD_DEFS` — field definitions (required/optional/labels) per create action
- `initCreateFlow()` — entry point; pre-fills any fields already in `parsed.value`, returns first missing required field prompt
- `advanceFieldCollection()` — merges new value into `collected`, tracks skipped optional fields via `_skippedOptional` sentinel, finds next missing field
- `executeCreate()` — strips `_skippedOptional` from POST body, POSTs to Payload, writes audit log
- `handleAwaitingFieldsRoundTrip()` — orchestrates round-trips

**Frontend (`useChatSession.ts`):**
- `awaitingFields` state: `{ action, field, collected, prompt } | null`
- 6th response chain: fires when `awaitingFields` is non-null and message is not a command verb
- Command-cancellation heuristic: if message starts with `update|add|create|new|list|change|edit|delete` or matches a `SUGGESTION_CHIPS` label, clears `awaitingFields` and falls through to cancel block
- `awaiting_fields` handler added to ALL 5 existing chains (previously missing from 2 caused raw JSON for portfolio/pricing)

**Optional field handling:**
- Client types "skip" → added to `_skippedOptional` sentinel, NOT stored as the string "skip"
- `_skippedOptional` is forwarded on every subsequent round-trip so skipped fields are never re-asked
- `_skippedOptional` is deleted from the POST body before sending to Payload

### 5.8 Conversation quality fixes (Phase 8, partially complete)

**`awaiting_value` guard (done):** Agent no longer surfaces raw errors when a required field is missing.

**FAQ "which field" step (specified, not yet run):** After selecting an FAQ record, agent always defaults to asking for the question field. No way to update the answer field or both. See §7 for the prompt.

**Safety-net catch in apir-tayo (specified, not yet run):** Defensive catch in `app/api/portal/agent/route.ts` for any non-2xx or error-shaped response from payload-poc. See §7 for the prompt.

### 5.9 Phase 11 — Response message quality pass (partially complete)

Pure wording/UX pass. No logic, state, schema, or API behavior changed.

1. **Proposal format** — replaced raw `key: "value"` YAML-style messages with natural-language proposals. `PROPOSAL DISPLAY RULES` added to `SYSTEM_PROMPT`. Dry-run wrapper bypassed — `newValue` (pre-formatted) is sent to client directly. **Bug fixed this session.**
2. **List display format** — replaced markdown bold with plain text. Collection-appropriate identifying snippets. `LIST DISPLAY RULES` added to `SYSTEM_PROMPT`.
3. **Clarifying question phrasing** — 12 field-specific conversational prompts replacing generic patterns. Optional fields include skip hint. `PROMPT PHRASING RULES` added to `SYSTEM_PROMPT`.
4. **Cancellation message** — `"Previous request cancelled."` → `"Got it, I've set that aside. What would you like to do?"`.

**Open bug — `url` field extraction (intentionally deprioritized):** Full-prompt create flow does not extract `url` written as `url https://...` — only `url: https://...` is matched. Agent asks "What's the URL?" even when provided. Sir Jeff demo was already conducted without this fix so it is not gating anything. See §7 for the ready-to-run prompt.

## 11. SiteSettings — Editable Homepage Headings

### 11.1 Schema
Built as a `site-settings` **collection**, slug `site-settings`, one record per Site enforced via `unique: true` on the `site` relationship field. Native Payload Globals cannot be scoped per tenant/site (the multi-tenant plugin only operates on collections).

No auto-seeding — a new Site has no `SiteSettings` record until an admin creates one. `fetchSiteSettings()` returns `null` in that case and the frontend falls back to hardcoded defaults.

### 11.2 Fields
Grouped into tabs by homepage section. All fields optional (no `required`).

| Tab name (API key) | Label | Fields |
|---|---|---|
| `hero` | Hero | `heroHeadline` (text), `heroSubheadline` (text) |
| `whyOnePage` | Why One Page | `whyOnePageTitle` (text), `whyOnePageParagraph` (textarea) |
| `howItWorks` | How It Works | `howItWorksTitle` (text), `howItWorksParagraph` (textarea) |
| `trust` | Trust | `trustSectionTitle` (text), `trustSectionParagraph` (textarea) |
| `cta` | CTA | `ctaTitle` (text), `ctaParagraph` (textarea), `ctaButtonText` (text), `ctaCaption` (textarea) |
| `footer` | Footer | `footerCopy` (text) |
| `custom` | Custom | `customFields` — array of `{ key (text, required), value (text, required) }` |

`customFields` exists to answer "what if a future site needs a heading section apir-tayo doesn't have" without a schema change. Access via `getCustomField(settings, key, fallback)` — not yet wired into any section component.

### 11.3 Critical implementation detail — tabs field nesting in REST API
Payload serializes `tabs` field groups as **nested JSON objects** in the REST API response — not flat at the document root.

```ts
// WRONG — returns undefined silently:
const headline = doc.heroHeadline;

// CORRECT — destructure the tab group first:
const headline = doc.hero?.heroHeadline;
```

`fetchSiteSettings()` handles this correctly already. Any future code reading site-settings from the API must follow this pattern.

### 11.4 Fallback behavior
Every section component renders `settings?.field ?? "<original hardcoded copy>"`. Leaving a field blank in Payload means the site reverts to the original hardcoded text — it will never show blank. This is intentional and safe.

### 11.5 Known visual tradeoff
The two-tone accent-color split on Hero, Why One Page, and How It Works headings disappears (collapses to a single plain-color span) whenever a CMS value is set. Accepted tradeoff for POC phase.

### 11.6 AI Agent — explicitly benched
SiteSettings is manual Payload admin CRUD only. No agent action, no dispatch wiring. If/when agent support is revisited, it cannot reuse `handleTextUpdate` — it would need a dedicated handler resolving directly to the one record for a given site (closer in shape to `handlePosts`).
