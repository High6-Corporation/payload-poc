IMPORTANT: The `EnabledCollectionsToggle` currently fetches custom collections for the current site via `useDocumentInfo().id`. When mounted on the Tenants edit form, `docId` will be a tenant ID, not a site ID. The component fetches `/api/custom-collections?where[site][equals]=<tenantId>`, which will return empty (tenant ID ≠ site ID). This is correct behavior — custom collections are site-scoped, not tenant-scoped. We should NOT modify the toggle component to fetch custom collections by tenant. The toggle on Tenants should show ONLY built-in collections.

However, there's a subtlety: when `docId` is a tenant ID and the `/api/custom-collections?where[site][equals]=<tenantId>` call fails or returns empty, the component correctly shows only built-in collections. This is the desired behavior. No change needed to EnabledCollectionsToggle.

But wait — the toggle currently hides its empty state ("No collections available") when `!hasCustom && !hasBuiltIn`. Since Tenants will have `hasBuiltIn: true` (after Step 1), the empty state won't trigger. If `BUILT_IN_COLLECTIONS` is still empty at this point, the component shows "No collections available". We populate it in Step 1, so this is fine.
